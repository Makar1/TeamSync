# TeamSync

Backend для управления командой внутри компании: пользователи, команды, задачи, встречи, оценки работы, календарь.

## Стек

- **FastAPI** + **Pydantic** — API и валидация
- **SQLAlchemy 2.0** + **Alembic** — ORM и миграции
- **PostgreSQL** (в Docker) — БД
- **JWT** (`python-jose`) — авторизация
- **pytest** + `TestClient` — тесты

## Структура проекта

- `app/models/` — SQLAlchemy-модели (по файлу на сущность)
- `app/schemas/` — Pydantic-схемы запросов/ответов
- `app/api/` — роутеры FastAPI
- `app/services/` — вынесенная бизнес-логика (см. "Детали реализации")
- `app/dependencies.py` — переиспользуемые проверки (`get_current_user`, `get_team_membership`)
- `alembic/` — миграции

## Установка и запуск

```bash
git clone <repo_url>
cd TeamSync

python -m venv venv
venv\Scripts\activate        # Windows
# source venv/bin/activate   # Linux/macOS

pip install -r requirements.txt
```

Скопируй `.env.example` в `.env` и при необходимости поправь значения:

```bash
cp .env.example .env        # Git Bash / Linux / macOS
# copy .env.example .env    # Windows PowerShell / cmd
```

Подними PostgreSQL:

```bash
docker-compose up -d
```

Примени миграции:

```bash
alembic upgrade head
```

Запусти сервер:

```bash
uvicorn app.main:app --port 8000
```

API доступен на `http://localhost:8000`, интерактивная документация — на `http://localhost:8000/docs`.

## Функциональность

### Пользователи

Регистрация и вход по email/паролю, пароль хранится только в виде bcrypt-хэша. Вход выдаёт JWT-токен, который дальше передаётся в заголовке `Authorization: Bearer <token>` на защищённых эндпоинтах. Есть смена пароля (с проверкой старого) и просмотр своего профиля.

### Команды

Пользователь создаёт команду и автоматически становится её менеджером. Остальные присоединяются по `invite_code` — случайной строке, которую сервер генерирует сам при создании команды. Роль (`member`/`manager`) — не глобальное свойство пользователя, а привязана конкретно к паре "пользователь + команда": один и тот же человек может управлять одной командой и быть рядовым участником в другой. Менеджер может менять роль участника или исключить его из команды.

### Задачи

CRUD-задачи внутри команды: название, описание, исполнитель, дедлайн, статус (`open` → `in_progress` → `done`, переход свободный, без принудительного порядка). Создавать/менять/удалять задачи может менеджер; менять **статус** может либо менеджер, либо назначенный исполнитель — это осознанно разные права: исполнитель отчитывается за свою работу, но не может произвольно переназначать задачи или менять их описание. У задач есть комментарии (доступны любому участнику команды).

### Оценки

Менеджер ставит оценку 1–5 и комментарий на задачу, но только если она уже в статусе `done`, у неё есть исполнитель, и она ещё не была оценена (одна оценка на задачу). Сотрудник может посмотреть все свои оценки и средний балл по ним — балл считается агрегирующим SQL-запросом (`AVG`), а не вычислением в Python.

### Встречи

Создать встречу может любой участник команды — организатор автоматически становится и участником. При создании/изменении времени или списка участников для **каждого** участника (включая организатора) проверяется, не пересекается ли новое время с любой другой его встречей — причём проверка идёт по всем его командам, а не только текущей: у человека одно расписание, независимо от того, в скольких командах он состоит. Отменить/изменить встречу может менеджер команды или организатор.

### Календарь

Один эндпоинт агрегирует в JSON личные задачи (по дедлайну) и встречи (по участию) пользователя за произвольный период — то, что нужно, чтобы построить фронтенд-календарь без похода в несколько разных ручек API.

## Детали реализации

**Проверка пересечений встреч.** Два интервала не пересекаются только если один целиком закончился до начала другого или начался после его конца — `NOT (new_end <= existing_start OR new_start >= existing_end)`. Сравнение нестрогое (`<=`/`>=`), поэтому встречи "встык" (одна заканчивается ровно когда начинается другая) не считаются конфликтом.

**Изоляция тестов через вложенные транзакции.** Обычный "открыл транзакцию — не закоммитил — откатил" не работает, потому что код самих эндпоинтов вызывает `db.commit()` изнутри. Решение — SAVEPOINT: внешняя транзакция никогда не коммитится, а каждый `db.commit()` эндпоинта на самом деле коммитит только вложенный SAVEPOINT, который тут же перезапускается через SQLAlchemy-event `after_transaction_end`. В конце теста откатывается только внешняя транзакция — и с ней разом всё, что происходило внутри, независимо от того, сколько раз код успел "закоммитить".

**IDOR-защита на каждом вложенном ресурсе.** Мало проверить, что пользователь залогинен — нужно проверять, что конкретный `task_id`/`meeting_id` действительно принадлежит команде, в которой он состоит (а не просто существует в базе). Поэтому почти все запросы к задачам/встречам фильтруются сразу по двум условиям: `id` **и** `team_id`.

**Защита от mass assignment.** Поля, которые должен решать сервер, а не клиент (`is_admin` у пользователя, `author_id`/`evaluator_id` у комментариев и оценок), никогда не принимаются из тела запроса — только из JWT-токена (`current_user`) или вычисляются на сервере.

**Частичный вынос бизнес-логики в `services/`.** Не все CRUD-операции — туда, где логика реально ветвится (overlap-проверка, сборка встречи с участниками, многошаговая валидация оценки), функции вынесены отдельно и кидают свои доменные исключения (`MeetingConflictError`, `TaskNotEvaluableError` и т.п., все — подклассы `ValueError`), а HTTP-код уже выбирает route-handler в `except`. Простые операции (создать команду, оставить комментарий) оставлены прямо в handler'е — для одного `db.add`+`db.commit` отдельный слой не оправдан.

## Справочник эндпоинтов

Полный список параметров и тел запросов — в Swagger (`/docs`). Здесь — обзор по ресурсам.

### Auth
| Метод | Путь | Доступ |
|---|---|---|
| POST | `/auth/register` | любой |
| POST | `/auth/login` | любой |

### Users
| Метод | Путь | Доступ |
|---|---|---|
| GET | `/users/me` | залогинен |
| PATCH | `/users/me/password` | залогинен |
| GET | `/users/me/evaluations` | залогинен — свои оценки + средний балл |

### Teams
| Метод | Путь | Доступ |
|---|---|---|
| POST | `/teams/` | залогинен — создатель становится `manager` |
| POST | `/teams/{team_id}/join` | залогинен, по `invite_code` |
| GET | `/teams/{team_id}/members/` | участник команды |
| PATCH | `/teams/{team_id}/members/{user_id}/role` | `manager` |
| DELETE | `/teams/{team_id}/members/{user_id}` | `manager` |

### Tasks
| Метод | Путь | Доступ |
|---|---|---|
| POST | `/teams/{team_id}/tasks` | `manager` |
| GET | `/teams/{team_id}/tasks` | участник команды |
| GET | `/teams/{team_id}/tasks/{task_id}` | участник команды |
| PATCH | `/teams/{team_id}/tasks/{task_id}` | `manager` |
| DELETE | `/teams/{team_id}/tasks/{task_id}` | `manager` |
| PATCH | `/teams/{team_id}/tasks/{task_id}/status` | `manager` или исполнитель задачи |
| POST | `/tasks/{task_id}/comments` | участник команды, к которой относится задача |
| POST | `/tasks/{task_id}/evaluation` | `manager`, только для задач в статусе `done` с назначенным исполнителем, одна оценка на задачу |

### Meetings
| Метод | Путь | Доступ |
|---|---|---|
| POST | `/teams/{team_id}/meetings/` | участник команды — создатель автоматически становится организатором и участником |
| GET | `/teams/{team_id}/meetings` | участник команды |
| PATCH | `/teams/{team_id}/meetings/{meeting_id}` | `manager` или организатор встречи |
| DELETE | `/teams/{team_id}/meetings/{meeting_id}` | `manager` или организатор встречи |

### Calendar
| Метод | Путь | Доступ |
|---|---|---|
| GET | `/calendar?from=...&to=...` | залогинен — свои задачи (по `due_date`) и встречи (по участию) за период |
